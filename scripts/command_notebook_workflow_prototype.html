What the notebook will show

      
A notebook is a document with explanations, small blocks of code, and their outputs. Both interfaces call the same program.

      
1 · Setup and paths
Open the project environment, then the guide. These filenames belong to the proposed implementation.
python -m pip install -r requirements.txt
python -m jupyterlab notebooks/physionet_walkthrough.ipynb
Copy the data and results paths from the fields above. Keep raw recordings in their existing folder; do not copy them into the notebook or results.
Reading an existing run? Run this setup cell, then skip directly to step 5. You need the saved result bundle, not the raw recordings.

      
2 · Check the inputs
Show the source version, file checks, required channel catalog, and saved participant assignment. Explain any stop and how to correct it.
run_step("check", "--data", str(DATA))

      
3 · Develop and freeze
Prepare the fitting and validation data, choose model settings, refit, complete the implementation checks, and measure resource use. Save the fixed recipe and readiness record before final testing.
Fitting people teach the model; validation people help choose its settings. The reserved final-test people do neither. The main analysis and the agreed near-flat EEG sensitivity analysis are both prepared here. “Sensitivity analysis” means repeating the comparison under the predeclared stricter rule.
run_step("develop")

      
4 · Deliberate final test
This notebook section displays a terminal command. It contains no executable final-test cell, so Run All cannot open the final test. The command requires completed development and the unchanged frozen recipe.
In the demo, use “3 · Final test” above. The real implementation task stops before this stage; the experiment task runs it.

      
5 · Read and verify the saved report
If final results are absent, show “Final test pending.” Otherwise rebuild the tables and plots from saved predictions, check the numbers, and display the saved report. No new model training.
status = json.loads((PROJECT / RUN / "run.json").read_text())
if status["final_stage"] in ("complete", "complete_with_unavailable"):
    run_step("report", "--verify")
else:
    print("Final test pending or incomplete. See step 4.")

      
6 · Explain and hand off
Read the sample counts and exclusions first. Then compare channel counts, inspect uncertainty, and explain limitations. Export the saved plots into slides. Share code and the permitted result bundle; keep raw participant recordings separate.

    


    

      
What appears in the results folder

      

      
Proposed file or folderWhy keep it?

        
run.jsonRun status, frozen recipe, dataset fingerprints, code version, dependency versions, checks, measured resource use, fit counts, and any failure.

        
manifests/Participant roles, recording sections, channel layouts, assumed units, and excluded data with reasons.

predictions/Model decision values, predictions and recorded labels, linked to the person, period, section, layout and analysis.

        
uncertainty/The same saved whole-person resampling draws used for every paired comparison within an analysis.

        
tables/, plots/, report.htmlScores, changes from full setup, layout variation, counts, exclusions, PNG plots and their explanations. Primary, sensitivity, and primary predictions on the sensitivity test data remain distinguishable.

      

      
Plot preview · channel-count comparison
Rows: EEG-channel counts. Columns: optical-group counts. A group keeps its paired signals; it is not a verified physical sensor. Dashes are placeholders, not zero scores.

      
Plot preview · change from full setup
For each count pair, show its mean score minus the full 32+8 score, in percentage points, with its paired approximate 95% interval. Mark zero change.
No values drawn: no experiment has run in this prototype.

      
Separate panel · variation among channel layouts
Show how much scores differ among channel sets at the same counts. This is separate from uncertainty caused by having few test people.

      
Also show baseline, Stress 1 and Stress 2 scores; mistaken/correct prediction counts; people/section counts; and exclusions. Main scores give each person equal influence and balance the task periods. No “acceptable loss” cutoff, best-layout ranking, or clinical claim.

      
Repeat the report or repeat the whole experiment?
Report replay: copy the completed result bundle and rerun report --verify in the recorded environment. Recalculate every reported number from saved predictions and draws; raw recordings are not needed. Missing or changed bundle files stop verification.
Full reproduction: use the saved code version, pinned dependencies, authorized recordings with matching fingerprints, identical participant/layout manifests and settings, and a new results folder. Run all four stages and compare outputs using the documented numerical tolerances. A new folder does not erase the fact that these final-test results have already been seen.
No exact cross-computer identity, runtime, or successful reproduction has been measured by this demo. The implementation must demonstrate these checks.

This is the target to benchmark, not a measured minimum requirement. Record measured memory, disk use and completed-fit counts during development; leave unknown values unknown.

Reuse the existing data folder and deterministic measurements, and process recordings in manageable batches. If a run stops, mark it incomplete and preserve its saved work. Never lower the agreed channel counts or change the participant assignment just to make the machine cope.
A frozen, unchanged interrupted run may continue from verified completed work. Changed code, settings or inputs require investigation and a separate run record. Preserve any prior final-test exposure in the record.
